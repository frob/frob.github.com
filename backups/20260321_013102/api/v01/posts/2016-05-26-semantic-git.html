This is a circular dependency that is good.</p> <h1>Semantic git-flow</h1> <h2>Background</h2> <p><a href="#tldr">skip TLDR;</a></p> <h3>Sematic Versioning</h3> <p>At a high-level Semantic Versioning aims to solve dependency issues by creating a standard versioning system that allows anyone to understand what has changed in a new version.</p> <h4>Example</h4> <p><em>1.2.3</em></p> <p><em><em>Major</em></em>.<em><em>Minor</em></em>.<em><em>Patch</em></em></p> <p>Major : Changing this is mandatory in the case of a backwards incompatible api change.</p> <p>Minor : Changing this is mandatory in the case of a backwards compatible api change or addition of new features.</p> <p>Patch : Changing this is mandatory in the case of any other change, that is not adding functionality or breaking backwards compatibility.</p> <h3>Git Flow</h3> <p>A git workflow that dictates what branches to make and why. A typical git-flow workflow will include 3+ branches:</p> <p><em>stable</em> : the current stable branch</p> <p><em>master</em> : the current development or HEAD</p> <p><em>master-feature</em> : where the work is actually accomplished</p> <p>The git flow workflow is designed so that:</p> <ul> <li>hot-fixing the stable product is always possible</li> <li>new features can be added to the stable product by merging in the feature branch</li> <li>git history remains linear to that it doesn&#39;t become git branch spaghetti</li> </ul> <h2>Semantic git <a name="tldr"></a></h2> <p>By merging these two ideas we can make it clear what is in development on any branch at any time and what that means to the product.</p> <h3>Stable</h3> <p><em>1.2.3</em> : By utilizing semantic versioning we can always keep it clear what our stable code is by using tags to snapshot stable code. In this way <em>stable</em> wouldn&#39;t be a branch but rather a tag. Since the <em>patch</em> number should increment any time there is a new stable release this should be a sane mechanism for it.</p> <h3>master</h3> <p><em>1.2.x</em> : There could me multiple master branches, one of any supported major.minor version combination. No work should be done directly on the master branches.</p> <h3>master-feature</h3> <p><em>1.2.x-feature</em> : It is obvious what is being worked on in the branch and what master version it is based on.</p> <h2>Workflow</h2> <ol> <li><p>Initialize git and create master branch</p> <ol> <li><code>git init</code></li> <li><code>git checkout -b 1.0.x</code></li> <li><code>git push -u origin 1.0.x</code></li> </ol></li> <li><p>Create new branch for &quot;Checkout Widget&quot; feature development</p> <ol> <li><code>git checkout -b 1.2.x-checkout-widget</code></li> <li><em>Work on project</em></li> <li><code>git fetch</code></li> <li><code>git pull --rebase origin 1.2.x</code></li> <li><code>git push origin 1.2.x-checkout-widget</code></li> </ol></li> <li><p>Create merge request in Gitlab or a pull request in github (shown here is what happens on the command line)</p> <ol> <li><code>git checkout 1.2.x-checkout-widget</code></li> <li><code>git pull --rebase 1.2.x</code></li> <li><em>test and peer review</em></li> <li><code>git checkout 1.2.x</code></li> <li><code>git merge 1.2.x-checkout-widget</code></li> </ol> <blockquote> <p>This is also handy if you are working on your own sub-feature branches that do not require further peer review.</p> </blockquote></li> <li><p>Create release tag and publish new release</p> <ul> <li><em>Patch release</em> <ol> <li><code>git tag 1.2.4</code> <em>Assumes the current release is 1.2.3</em></li> <li><code>git push origin 1.2.4</code></li> </ol></li> <li><em>Minor release</em> <ol> <li><code>git tag 1.2.0</code> <em>Assumes the current release is 1.1.&lt;any-number&gt;</em></li> <li><code>git push origin 1.2.0</code></li> <li><code>git checkout -b 1.3.x</code></li> <li><code>git push -u origin 1.3.x</code></li> </ol></li> </ul></li> </ol> <blockquote> <p>Notice the new Minor Release comes from the branch of the same name. Same is true of Major Releases. As soon as it is known that backwards compatibility will be broken, then new Major Release branch should be made. Before work is started on a new feature, a new Minor Release branch should be made.</p> </blockquote> " } ]
